# TessariDB query builder — rendering contract, version 1

**Builder contract version 1.0.** Drafted 2026-09-01.

Status: **draft, authoritative for builders.**

> **This is language, not protocol.** §6 of `protocol-v1.md` puts the query
> language deliberately outside the protocol, and that stands: a node speaks the
> wire and HTTP protocols, and TessariQL is what travels over them rather than
> part of them. This document sits beside the protocol rather than inside it, and
> a client may implement the protocol completely while ignoring every word here.

## Why it exists anyway

§6 states the obligation in the same breath as the exclusion: a query builder
"produces the grammar the server's own parser accepts, and that is proven by
round-tripping built queries through that parser — not by inspection."

That proof is available in exactly one place — the server's workspace — and no
client may look there. A Rust client cannot link the parser; a Python or Go
client could not link it even if it were allowed to. So each language's builder
would arrive at its own rendering, every one of them plausible, and the
divergence would surface as a user reporting that the same query behaves
differently depending on which client wrote it.

This document is the substitute, and it is weaker in a way worth naming. It
states what a builder **must render**; the corpus beside it
(`conformance/queries-v1.json`) states the same thing case by case, executably.
Together they make every language's builder agree with every other. Neither makes
a builder agree with the *parser* — only a running node does that, and every
client is expected to run the corpus against one (§7 of the protocol document
already requires verification against a running node, and this is the same rule
applied to the same artifact).

**Provenance, stated because it changes what the corpus proves.** The value
corpus is generated by an implementation written from `protocol-v1.md` alone, so
its agreement is evidence the *document* is sufficient. This document is not in
that position: version 1 was written by reading the rendering the reference Rust
builder already emitted, so it **describes** a rendering rather than having
dictated one. What the corpus therefore proves is that two implementations of
this document agree, and that the result is accepted and executed correctly by a
node. What it does not prove is that this rendering is the one anybody would have
chosen. Later versions are dictated by this document; version 1 is a record.

---

## 1. Scope

A builder covered by this document offers exactly four statements — `SELECT`,
`CREATE`, `UPDATE`, `DELETE` — over a single collection, with the clauses named
in §4. Anything else is written by the caller as a script and sent as one, which
is always available.

A builder **MUST NOT** grow a clause that is not in this document without the
document growing it first, because a clause one language has and another does not
is the divergence this contract exists to prevent.

---

## 2. The one guarantee

**A caller's value never reaches the statement text.** Every value becomes a
bound parameter; the text carries the parameter's reference, and the value
travels beside it in the value codec of §4 of the protocol document.

This is not a builder convenience. It is clause 7 of the protocol's own
conformance list: a client **MUST** carry parameter values through the value
codec and **MUST NOT** interpolate them into script text.

A builder that formatted values into the text would destroy the property the
whole surface is designed around, and would do it invisibly, because the output
still looks correct.

---

## 3. Names, and why they are not values

Table names, field names and sort directions are **grammar**. A parameter may not
supply one, so they are written into the text directly.

That is safe only because each is checked first, and the check is **in front of**
the interpolation rather than trusted to be somewhere else.

A **name** is:

```
name  ::=  ( ALPHA / "_" ) *( ALPHA / DIGIT / "_" )
ALPHA ::=  %x41-5A / %x61-7A          ; ASCII letters only
DIGIT ::=  %x30-39
```

- A builder **MUST** refuse a string that is not a name, in every position that
  takes one, and **MUST NOT** quote or escape it into acceptance. Quoting turns a
  caller's mistake into a statement that runs and means something else.
- The check is deliberately **narrower** than what the node's lexer accepts. A
  guard that reasons about what a lexer would do has to be re-checked every time
  the lexer changes; one that accepts only the production above does not.
- The refusal is reported as `not-a-name` in the corpus, carrying which position
  the name was in.

## 4. Rendering

Every statement ends with a single `;` and contains no newline. Tokens are
separated by exactly one space except where a production below says otherwise.

### 4.1 Parameter references

Parameters are named `p0`, `p1`, … in **binding order**, counting from zero, and
are referenced as `$p0`. The counter is **per statement**: `$p0` in one query is
unrelated to `$p0` in the next.

Binding order is defined by each production below, and is the order a reader of
the rendered text meets the references left to right.

### 4.2 `SELECT`

```
SELECT <projection> FROM <table>
       [ WHERE <filter> ]
       [ ORDER BY <ordering> ]
       [ START <count> ]
       [ LIMIT <count> ] ;
```

rendered on one line, each present clause preceded by one space.

- **`<projection>`** is `*` when no field is named; otherwise the named fields in
  **the order they were named**, joined by `", "`.
- **`<ordering>`** is `<name> ASC` or `<name> DESC` per field, in the order the
  orderings were added, joined by `", "`. The direction is always written out,
  including when it is the node's default, so the statement says what it does.
- **`<count>`** for `START` and `LIMIT` is a decimal unsigned 64-bit integer
  written literally. It is **not** a parameter: it is part of the statement's
  shape rather than data, and a builder receives it as an integer, so there is
  nothing a caller can smuggle syntax through.
- `START` precedes `LIMIT` when both are present.
- A second `WHERE` **replaces** the first rather than combining with it. A
  builder that silently `AND`ed two filters would make a duplicated call look as
  though it had worked.

### 4.3 Filters

```
filter     ::=  comparison / conjunction / disjunction
comparison ::=  <field> SP <operator> SP <parameter-ref>
conjunction::=  "(" filter " AND " filter ")"
disjunction::=  "(" filter " OR " filter ")"
operator   ::=  "=" / "!=" / "<" / "<=" / ">" / ">="
```

- A conjunction and a disjunction are **fully parenthesised**; a bare comparison
  is not. Parentheses are not an aid to reading — a builder does not depend on
  the parser and therefore does not get to assume how `AND` and `OR` associate.
  Full parenthesisation makes the tree the caller built the tree that runs.
- Values bind **depth-first, left to right**, so a comparison's parameter number
  is fixed by its position in the rendered text.

### 4.4 `CREATE`

Two forms, and the difference is whether the caller supplies the identity.

```
CREATE <table>:<parameter-ref> = <object> ;      ; caller's identity
CREATE <table> = <object> ;                      ; store allocates one
```

- The identity binds **first** (`$p0`), before any field, in the identity form.
- The identity travels as a **parameter**, never as text, so an identity that
  happens to spell a statement is a record with an unusual name.
- A `CREATE` with no fields is **refused** as `incomplete`, not rendered with an
  empty object.

### 4.5 `UPDATE`

```
UPDATE <table>:<parameter-ref> SET <field> = <parameter-ref>
                                 *( ", " <field> " = " <parameter-ref> ) ;
```

- The identity binds first, then the assignments.
- `SET` changes the named fields only. The whole-record replacement form is not
  what a builder with a `set` method should quietly emit — a caller who wants a
  replacement asks for `CREATE`, where the word says so.
- An `UPDATE` with no assignments is **refused** as `incomplete`.

### 4.6 `DELETE`

```
DELETE <table>:<parameter-ref> ;
```

### 4.7 Objects

```
object ::=  "{ " <field> ": " <parameter-ref> *( ", " <field> ": " <parameter-ref> ) " }"
```

Note the spaces immediately inside the braces.

### 4.8 Field order in an object or a `SET`

Fields render in **ascending order of their names**, compared byte by byte as
UTF-8 — *not* in the order the caller set them.

This is a rendering rule rather than an implementation accident, and stating it
is what lets a corpus carry a `set` as an unordered JSON object: two builders
given the same fields in different orders must produce the same text and the same
parameter numbering. A builder preserving call order would render a different
statement for a caller who wrote the same thing in a different order, and the
corpus could not describe it.

---

## 5. Refusals

A builder reports two refusal reasons, and they are the corpus's vocabulary:

| reason | when |
|---|---|
| `not-a-name` | a table, field or other grammatical position was given a string that is not a name (§3) |
| `incomplete` | a statement that cannot be rendered at all — a `CREATE` or `UPDATE` with no fields |

A refusal is returned to the caller. It is never a rendered statement that the
node will refuse instead, because the caller is here now and the node is not.

---

## 6. Conformance

A conforming builder:

1. **MUST** render each case in `conformance/queries-v1.json` to exactly the
   stated `script`, with exactly the stated `parameters`.
2. **MUST** refuse each case carrying `refused`, with the stated reason, and
   **MUST NOT** render it.
3. **MUST** verify the corpus in the language's own test suite, and **MUST** fail
   rather than skip when the corpus file is absent — a suite that passes having
   found nothing to check reports coverage it does not have.
4. **SHOULD** additionally execute every rendered case against a running node
   with its parameters bound, and assert the node accepts and runs it. This is
   the only check that reaches the parser, and it is a `SHOULD` only because a
   public client repository may have no node to reach; where one is reachable it
   is the strongest evidence available.
5. **MUST NOT** add a clause, statement or refusal reason that this document does
   not describe.

The corpus and this document move together. A change to a rendering is a change
to both, in the same commit, and regenerating the corpus is part of changing the
grammar rather than something done afterwards.

---

## 7. Open

- **Nothing here reaches the parser.** Point 4 above is the substitute and is not
  exact: a node that stopped accepting a rendering would fail the corpus run of
  whoever ran it against a node, and nobody else. A node-side "would you parse
  this?" answer would make it exact, and is not specified.
- **Version 1 describes rather than dictates** — see the provenance note at the
  top. The first rendering change made through this document rather than into it
  closes that gap.
